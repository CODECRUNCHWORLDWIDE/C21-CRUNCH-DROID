# Mini-Project — Profile the reader app's cold start, prove the win

This week you take the **Week-11 reader app** (the Material 3 reader with dynamic color and edge-to-edge), wire up a `:benchmark` module, measure its cold start as a distribution, generate and package a **Baseline Profile**, enable **R8**, measure again, and **document the cold-start improvement with real numbers**. By the end you have an app that's measurably faster to launch, a committed profile, and a `PERF.md` that proves the win the way a senior engineer's performance PR does.

The point of the project is not "make the app faster" — it's to run the **measure → fix → re-measure loop** on real hardware and *prove* the result as a distribution against a noise floor. That before/after — "cold start was 520ms median with no profile; the Baseline Profile and R8 took it to 340ms; here's the macrobenchmark output and the noise floor proving it's real" — is the senior instinct this week installs, and it's the exact deliverable the capstone requires (a Baseline Profile demonstrated to cut cold start by ≥20%).

This is the *same app* you already built in Week 11 — you're not rebuilding it, you're instrumenting and optimizing it. If you don't have the Week-11 reader app, any Compose app with a list-then-detail flow and a release build works; the measurement is the point.

## Where you're starting from

The Week-11 reader app (or equivalent): a Compose app with a Material 3 theme, an article list screen, and an article detail screen, that you can build in release. You'll add:

- A `:benchmark` module (the `com.android.test` plugin, targeting `:app`).
- The `androidx.baselineprofile` Gradle plugin and a profile generator.
- R8 enabled on the release build type.

## What you're building toward

By the end you have:

- A `:benchmark` module with a `StartupBenchmark` (cold start, `StartupTimingMetric`) and a `BaselineProfileGenerator`.
- A no-profile baseline measurement (P50 + P90, ≥20 iterations, on a named real device) and an established noise floor.
- A committed `baseline-prof.txt` generated by driving the reader's cold-start journey (launch → scroll the list → open an article).
- R8 enabled on release, with any necessary keep rules (most ship as consumer rules) and the `mapping.txt`/`usage.txt` outputs inspected.
- A with-profile measurement, and a documented cold-start improvement.
- A `PERF.md` reporting the before/after distributions and the win — ≥20% at P50.

## Milestone 1 — The `:benchmark` module and the "before" (≈ 2 h)

Create the `:benchmark` module targeting `:app` (lecture 1, §2). Write `StartupBenchmark` measuring cold start with `CompilationMode.None()`:

```kotlin
@RunWith(AndroidJUnit4::class)
class StartupBenchmark {
    @get:Rule val rule = MacrobenchmarkRule()

    @Test
    fun coldStartup_noProfile() = rule.measureRepeated(
        packageName = "com.crunch.reader",
        metrics = listOf(StartupTimingMetric()),
        iterations = 20,
        startupMode = StartupMode.COLD,
        compilationMode = CompilationMode.None()
    ) {
        pressHome()
        startActivityAndWait()
    }
}
```

Run on a **real device** (`./gradlew :benchmark:connectedBenchmarkAndroidTest`). Record P50 and P90.

Decisions you must defend in review:

- **Why `CompilationMode.None()` for the baseline, not `Partial()`?** Because the no-profile worst case is the honest starting point — what a fresh install looks like before any profile. You measure `None()` first so the `Partial()` "after" has something to be compared against (lecture 1, §4).
- **Why a real device, not the emulator?** Emulated hardware, host-CPU contention, and no thermal reality make emulator startup numbers meaningless. A mid-range physical device finds your real bottlenecks (lecture 1, §2).

## Milestone 2 — Establish the noise floor (≈ 0.5 h)

Run the *same* `None()` benchmark a second time. The difference between the two P50s is your noise floor. Record it: "noise floor ≈ Xms over two identical runs." This is the number your final claimed improvement must exceed to be believable. Skipping this is how engineers over-claim a 10%-plus-noise win as 35%.

## Milestone 3 — Generate the Baseline Profile (≈ 1.5 h)

Add the `androidx.baselineprofile` plugin (`baselineProfile(project(":benchmark"))` in the app) and a generator that drives the reader's cold-start journey:

```kotlin
@RunWith(AndroidJUnit4::class)
class ReaderBaselineProfileGenerator {
    @get:Rule val rule = BaselineProfileRule()

    @Test
    fun generate() = rule.collect(
        packageName = "com.crunch.reader",
        includeInStartupProfile = true
    ) {
        pressHome()
        startActivityAndWait()
        device.findObject(By.res("article_list")).fling(Direction.DOWN)
        device.waitForIdle()
        device.findObject(By.res("article_item_0")).click()   // open the first article
        device.waitForIdle()
    }
}
```

(You'll need stable resource IDs / test tags on the list and items — add `Modifier.testTag(...)` where needed; you already know this from Week 17.) Run `./gradlew :app:generateBaselineProfile`, confirm `app/src/release/generated/baselineProfiles/baseline-prof.txt` appears, and **commit it**.

## Milestone 4 — Enable R8 and package the profile (≈ 1.5 h)

Enable R8 on the release build:

```kotlin
buildTypes {
    release {
        isMinifyEnabled = true
        isShrinkResources = true
        proguardFiles(getDefaultProguardFile("proguard-android-optimize.txt"), "proguard-rules.pro")
    }
}
```

Build the release (`./gradlew :app:assembleRelease`). Two things to verify:

- **The profile packaged:** unzip the AAB/APK, confirm `assets/dexopt/baseline.prof` exists.
- **R8 didn't break anything:** run your Week-17 Espresso smoke (or manually exercise the app) against the *minified* build. If a reflection path (serialization, DI) breaks, write the *narrowest* keep rule (lecture 2, §2) — don't disable R8. Read `app/build/outputs/mapping/release/usage.txt` to confirm R8 removed only what you expected.

## Milestone 5 — Measure the "after" and verify (≈ 1.5 h)

Add the with-profile benchmark and run it on the same device:

```kotlin
@Test
fun coldStartup_withProfile() = rule.measureRepeated(
    packageName = "com.crunch.reader",
    metrics = listOf(StartupTimingMetric()),
    iterations = 20,
    startupMode = StartupMode.COLD,
    compilationMode = CompilationMode.Partial(BaselineProfileMode.Require)
) {
    pressHome()
    startActivityAndWait()
}
```

`Require` makes the benchmark fail if no profile is present, so a passing run proves the profile packaged. Verify ART used it independently with `adb shell dumpsys package com.crunch.reader | grep -A2 "Dexopt state"`. Record P50 and P90.

## Milestone 6 — Document the win (≈ 1 h)

Write `PERF.md`:

- The before (`None()`) and after (`Partial(Require)`) distributions — P50 and P90 for each.
- The noise floor, and confirmation the delta exceeds it.
- The cold-start improvement, ms and %, at both percentiles — target ≥20% at P50.
- The device named, the iteration count stated.
- One sentence on *what* the profile compiled (read the trace or the `baseline-prof.txt` — the Compose runtime and your screen composables are the usual big wins).
- Honesty: if the win is under 20%, say why and what you'd try (broaden the journey, check the profile packaged, defer an eager initializer — lecture 2, §4).

- [ ] The "after" measured with `CompilationMode.Partial(Require)`, same device/iterations, P50 + P90 recorded.

- [ ] Build with **0 warnings, 0 errors**.

## Stretch goals

- **Defer an eager initializer.** Open a startup trace (each benchmark iteration captures one). Find an SDK or component initializing on the startup path; move it off with the App Startup library or lazy init (lecture 2, §4); re-measure and add the additional delta to `PERF.md`. Two levers, measured separately.
- **StrictMode audit.** Enable StrictMode in debug (`detectDiskReads().detectNetwork().penaltyLog()`), launch the app, and fix any main-thread I/O it flags on the startup path. Note what you found.
- **A `FrameTimingMetric` scroll benchmark.** Add a benchmark that scrolls the article list and measures frame durations (jank), separate from startup. Report the P90 frame time.
- **CI gate (preview of Week 21).** Wire a Gradle check that fails if `baseline-prof.txt` is missing or the release build doesn't package it. A regression guard for the profile.
