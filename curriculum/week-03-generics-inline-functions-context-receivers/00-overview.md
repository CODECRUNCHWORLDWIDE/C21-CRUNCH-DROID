# Week 03 — Generics, inline functions, context receivers

Welcome to Week 03 of **C21 · Crunch Droid**, and the last of the "Kotlin as a language" weeks before coroutines take over in Week 04. Week 01 taught you to write Kotlin that does not read like translated Java; Week 02 gave you the algebraic core — null safety, sealed types, data classes, inline value classes. This week is the one that separates people who *use* Kotlin's standard library from people who could have *written* it. We go deep on three machineries that look like syntax and are actually the load-bearing walls of every Kotlin API you already lean on: **generics and variance**, **inline functions with reified type parameters**, and **context receivers** (the Kotlin 2.x feature that finally lets you write extension-like code against more than one receiver without smuggling it through a parameter).

The reason this week exists is that the entire Kotlin and Android ecosystem is built on these three. `buildList { }`, `apply`, `with`, `runBlocking`, `Flow.map`, `viewModelScope.launch`, every Compose `@Composable` lambda receiver, Hilt's `@Provides`, Gradle's `dependencies { }` block — they are not magic. They are higher-order functions, often `inline`, frequently reified, and increasingly written against context receivers. By the end of the week you should be able to look at `inline fun <reified T> Gson.fromJson(json: String): T` and explain — out loud, to a staff engineer — exactly what the compiler does with `reified`, why it *requires* `inline`, and what would break if you removed either keyword.

The thing this week hammers on is that **`inline fun <reified T>` is not a parlor trick.** Beginners treat `reified` as "the keyword that lets me write `T::class`," memorize that it needs `inline`, and move on. That is a recipe, not an understanding. The truth is that Kotlin generics — like Java's — are **erased** at runtime: `List<String>` and `List<Int>` are the same `List` once compiled, and a normal generic function genuinely *cannot* know what `T` was. Reification does not change erasure; it sidesteps it by **inlining the function body at every call site and substituting the concrete type there**, so `T::class` becomes a literal `String::class` in the generated bytecode. Understanding that one sentence — reification is a call-site substitution made possible by inlining, not a runtime type token — is what makes `crossinline`, `noinline`, and the "you can't store a `reified T` in a field" restriction all obvious instead of arbitrary.

We then add **variance** — the `in`/`out` annotations that decide whether a `List<String>` is acceptable where a `List<Any>` is expected — because variance is the other half of "generics you can explain out loud," and it is the single most common thing a senior Android candidate fumbles in an interview. And we close with **context receivers**, the Kotlin 2.x capability that lets a function declare "I can only be called where a `LoggingContext` and a `TransactionScope` are both in scope," which is how modern Kotlin DSLs and the next generation of Android architecture libraries pass ambient capabilities without threading them through every signature.

The week's mini-project is a typed event bus — **`kt-bus`** — built on reified generics and inline subscription functions, published to `mavenLocal` as a real Gradle subproject. You will write `bus.subscribe<UserLoggedIn> { event -> ... }` and `bus.post(UserLoggedIn(id))` and have the type system route each event to exactly the right handlers with zero casts and zero `Class<*>` parameters in your public API — because `reified` captured the type for you at the call site. That API, the one that feels effortless to *call*, is effortful to *write*, and writing it is the skill this week installs.

## Learning objectives

By the end of this week, you will be able to:

- **Explain** type erasure: that `List<String>` and `List<Int>` share one runtime class, why a normal generic function cannot recover `T`, and what bytecode a generic function actually compiles to.
- **Read and write** declaration-site variance (`out T`, `in T`) and use-site variance (`List<out Any>`, type projections), and state out loud why `Producer<out T>` is covariant and `Consumer<in T>` is contravariant.
- **Trace** how `inline` works: the function body and its lambda arguments are copied into the call site, eliminating the lambda object allocation, and why that is what enables non-local returns and reified types.
- **Use** `reified` type parameters correctly: write `inline fun <reified T> ...` that calls `T::class`, `is T`, or `T::class.java`, and explain why `reified` requires `inline` and cannot be stored or used from a non-inline context.
- **Apply** `crossinline` and `noinline` deliberately: know that `crossinline` forbids non-local returns from a lambda (needed when the lambda is invoked from another execution context) and `noinline` opts a single lambda parameter out of inlining.
- **Write** higher-order functions and understand SAM conversion: when a Kotlin function type becomes a Java single-abstract-method interface, and when `fun interface` earns its keep.
- **Design** APIs with context receivers (Kotlin 2.x `context(...)` declarations): declare a function that requires one or more receivers in scope, call it inside a `with(...)`-provided context, and explain why context receivers beat both extra parameters and extension receivers for ambient capabilities.

## Prerequisites

This week assumes you have completed **C21 weeks 1–2**, or have equivalent fluency. Specifically:

- You can read and write idiomatic Kotlin 2.x — `val`/`var`, data classes, sealed classes, lambdas, trailing-lambda syntax, and function types `(A) -> B` — Weeks 1–2. This week is *about* function types; if `(String) -> Unit` is opaque, re-read Week 1.
- You understand the JVM at the level Week 01 set: that Kotlin compiles to JVM bytecode, that you can inspect it with `javap`, and that "the compiler rewrites your code" is a thing that actually happens. We read bytecode again this week to make inlining and erasure concrete.
- You are comfortable with extension functions — `fun String.shout(): String` — from Week 01. Context receivers are the generalization of the extension receiver to *multiple* ambient receivers, so the extension-function mental model is the on-ramp.
- Your toolchain is set from Week 01: JDK 17, Kotlin 2.0+, a Gradle Kotlin DSL project. This week you add a second Gradle subproject and publish it to `mavenLocal`, so make sure `./gradlew` runs cleanly first.

**Toolchain.** JDK 17 (or 21), Kotlin **2.0+** with the K2 compiler. Context receivers are an experimental Kotlin 2.x feature gated behind the compiler flag `-Xcontext-receivers` (in Gradle: a `freeCompilerArgs` entry); we turn it on this week and discuss its experimental status and the in-progress evolution to *context parameters* honestly. `javap` ships with the JDK. Everything this week runs on the **JVM** — no Android device, no emulator. `kt-bus` is a pure-Kotlin library; the Android-specific weeks start at Week 06.

## Topics covered

- **Type erasure.** What the JVM keeps and throws away about generics. Why `List<String>` and `List<Int>` are one class at runtime, why `if (x is List<String>)` does not compile, and what `Array<T>` does differently (it keeps a component type).
- **Declaration-site variance.** `out T` (covariance — `T` only appears in *out* positions, return types) and `in T` (contravariance — `T` only in *in* positions, parameters). Why `List<out E>` is covariant by declaration and `MutableList<E>` is invariant.
- **Use-site variance and projections.** `Array<out Any>`, the `*` star-projection, and when you reach for a use-site projection because you do not own the declaration.
- **Higher-order functions and function types.** `(A) -> B`, receiver function types `A.() -> B`, passing and returning functions, and the runtime cost of a lambda (a `Function` object allocation) that `inline` removes.
- **`inline` functions.** The body-and-lambdas-copied-to-call-site transform. Why it removes the lambda allocation, why it enables non-local `return` from a lambda, and why over-inlining bloats bytecode (use it for lambda-taking functions, not everywhere).
- **`reified` type parameters.** Recovering the concrete type at the call site via inlining. `T::class`, `is T`, `T::class.java`. The hard restriction: `reified` requires `inline`, and you cannot store `T` or use it where there is no call site (no `reified` in a class, no `::class` on a non-reified `T`).
- **`crossinline` and `noinline`.** `crossinline`: the lambda is inlined but may not do a non-local return, because it is invoked from a different execution context (e.g. inside another lambda or a `Runnable`). `noinline`: this one lambda parameter is *not* inlined, so you can store it or pass it on.
- **SAM conversion and `fun interface`.** When a Kotlin lambda is converted to a Java single-abstract-method interface automatically, why Kotlin function types do *not* SAM-convert to a Kotlin interface unless it is a `fun interface`, and when defining a `fun interface` is the right call.
- **Context receivers (Kotlin 2.x).** `context(Logger) fun doWork()` — declaring a function that requires receivers in scope, calling members of those receivers without qualification, providing them with `with(...)`, and composing multiple context receivers. The difference from extension receivers and from plain parameters, and the honest status (experimental; evolving toward context parameters).

## The "no casts in the public API" promise

Every week of Crunch Droid adds one production-grade contract a senior reviewer actually checks. This week's:

> **A typed API must not leak `Class<*>`, `Any`, or unchecked casts to its callers.** If a caller has to write `bus.subscribe(UserLoggedIn::class.java) { it as UserLoggedIn }`, the API failed — the type information was available at the call site and you threw it away. Capture it with `reified`, route on it internally, and give the caller `bus.subscribe<UserLoggedIn> { event -> ... }` with `event` already typed. Inside the library you will cast exactly once, in exactly one place, guarded by the type you reified — and that single internal cast is *safe* because the `reified` type proved it.

You will prove this in `kt-bus`: the public `subscribe` and `post` take no `Class` parameter and force no caller cast, and `javap` on a call site shows the concrete event type baked into the generated bytecode. "It compiles" is not the test — an API with `Any` everywhere also compiles. The test is whether a caller can ever get a `ClassCastException` from *your* API. With reified routing, they cannot.

## A note on what's not here

Week 03 is the *generics and inline machinery* week. It deliberately does **not** cover:

- **Coroutines and `suspend`.** `suspend` functions, `inline` in the context of `suspend`, and `crossinline` as it appears in coroutine builders are **Week 04**. This week's `crossinline` treatment is the general rule; Week 04 shows the specific coroutine reason it matters.
- **Flow operators.** `Flow.map`, `flatMapLatest`, and friends are higher-order inline functions you will appreciate more for having done this week — but they are **Week 05**.
- **Compose's `@Composable` lambdas.** A `@Composable () -> Unit` is a receiver-less function type the compiler instruments specially; the inline/reified mental model helps, but Compose is **Week 07** onward.
- **Android-specific generics pain.** `ViewModelProvider`, `Bundle` type tokens, `Parcelable` generics — the places Android makes you fight erasure — show up when you hit them in Phase 2 and 3. This week is the pure-Kotlin foundation.
