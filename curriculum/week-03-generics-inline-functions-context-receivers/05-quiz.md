# Week 03 — Quiz

Thirteen questions. Take it with your lecture notes closed. Aim for 11/13 before moving to Week 04. Answer key with explanations at the bottom — don't peek.

**Q1.** At runtime, what is the relationship between `Box<String>` and `Box<Int>`?

- A) Two distinct classes generated by the compiler.
- B) The same class — the type argument is erased; both are just `Box`.
- C) The same class, but each instance stores a `Class<T>` token.
- D) `Box<Int>` is a subclass of `Box<String>`.

---

**Q2.** Why does `if (x is List<String>)` fail to compile?

- A) `List` isn't `Comparable`.
- B) Type erasure removed `<String>`; at runtime there's only `List`, so the check can't be performed. Use `List<*>` or a reified type parameter.
- C) `is` doesn't work on interfaces.
- D) You must write `x is MutableList<String>`.

---

**Q3.** A type is declared `interface Producer<out T> { fun produce(): T }`. Which is true?

- A) `Producer<Cat>` is a subtype of `Producer<Animal>` (covariant), because `T` is only produced.
- B) `Producer<Animal>` is a subtype of `Producer<Cat>` (contravariant).
- C) They're unrelated; `out` makes it invariant.
- D) `out` means `T` can only be a parameter, never a return.

---

**Q4.** Why must `MutableList<E>` be **invariant** (neither `in` nor `out`)?

- A) Mutable types can never be variant.
- B) It both produces `E` (via `get`) and consumes `E` (via `add`); allowing covariance would let you `add` a `Dog` to a `MutableList<Cat>`, and contravariance would make `get` return the wrong type.
- C) `MutableList` isn't a real interface.
- D) Invariance makes it faster.

**Q5.** What does `inline` actually do to a function and its lambda arguments?

- A) Runs it on a background thread.
- B) Copies the function body — and each lambda argument's body — into the call site, eliminating the `Function` object allocation for those lambdas.
- C) Caches the result.
- D) Marks it for the JIT to optimize later.

---

**Q6.** Why does `reified` require `inline`?

- A) Style convention; it would work without it.
- B) Reification works by substituting the concrete type into the function body *at the call site*; that's only possible if the body is inlined there. No inlining → no call site to substitute into → `T` stays erased.
- C) `inline` makes the function thread-safe, which `reified` needs.
- D) Because `reified` stores a `Class<T>` field that `inline` initializes.

**Q7.** Which statement about a `reified T` is correct?

- A) You can declare a `reified` type parameter on a class.
- B) You can store a `reified T` in a field for later use.
- C) Inside an `inline fun <reified T>`, you can write `x is T`, `x as T`, and `T::class`, because the concrete type is substituted at each call site.
- D) `reified` defeats type erasure for all generic code in the program.

**Q8.** You have `inline fun process(crossinline block: () -> Unit)`. What does `crossinline` mean?

- A) The lambda runs on another thread automatically.
- B) The lambda is still inlined (no allocation), but it may **not** do a non-local return — because it's invoked from a different execution context (e.g. inside another lambda or a `Runnable`).
- C) The lambda is not inlined at all.
- D) The lambda must be the last parameter.

**Q9.** When would you mark a lambda parameter `noinline`?

- A) To make it faster.
- B) When you need to **store** that lambda (in a field/list) or **pass it on** to a non-inline function — an inlined lambda has no object to store, so `noinline` keeps it a real `Function` instance.
- C) To allow a non-local return.
- D) Whenever the function has more than one parameter.

**Q10.** You write `Thread { doWork() }.start()` and it compiles, converting the lambda to a `Runnable`. What made that work?

- A) `Thread` is `inline`.
- B) SAM conversion: `Runnable` is a Java single-abstract-method interface, so Kotlin auto-wraps the lambda as a `Runnable` instance.

**Q11.** You define `interface Validator { fun validate(s: String): Boolean }` (no `fun` keyword) and try `val v = Validator { it.isNotBlank() }`. What happens?

- A) It works — Kotlin SAM-converts any single-method interface.
- B) Compile error — Kotlin interfaces don't SAM-convert unless declared `fun interface`. Add `fun` to make `Validator` a functional interface.

**Q12.** What does `context(Logger, Clock) fun recordEvent(name: String)` declare, and how do you call it?

- B) A function that requires a `Logger` and a `Clock` as receivers in scope; call it inside `with(logger) { with(clock) { recordEvent(name) } }`, and it can call `log(...)`/`now()` unqualified. Calling it without the context is a compile error.
- C) A function that creates a `Logger` and a `Clock` internally.

**Q13.** In a typed event bus, `inline fun <reified T> subscribe(noinline handler: (T) -> Unit)` stores the handler in a `Map<Class<*>, MutableList<(Any) -> Unit>>` after one `handler as (Any) -> Unit` cast. Why is that single cast safe?

- A) It isn't; it's a latent bug.
- B) Because `post` only ever invokes a handler with an event whose `javaClass` equals the key the handler was filed under (the `reified T`'s class), so the handler's `Any` argument is always actually a `T` — the reified type tied the handler to its key.
- C) Because `@Suppress` makes casts safe.
- D) Because `noinline` checks the type at runtime.

## Answer key

**Q1 — B.** Type erasure: `Box<String>` and `Box<Int>` compile to the one class `Box`; the type argument exists only at compile time. `a::class == b::class` is `true`. (Lecture 1, §1.)

**Q2 — B.** The `<String>` is erased, so at runtime there's only `List` and the check can't be performed; the compiler refuses. `List<*>` (checkable) or a reified type parameter are the ways through. (Lecture 1, §2.)

**Q3 — A.** `out T` means `T` appears only in *out* (return) positions, which makes the type **covariant**: `Producer<Cat>` is a subtype of `Producer<Animal>`, because reading a `Cat` out is always a valid `Animal`. (Lecture 1, §4.)

**Q4 — B.** `MutableList` both produces (`get(): E`) and consumes (`add(e: E)`) `E`, so it must be invariant. Covariance would let you `add` a `Dog` to a `MutableList<Cat>`; contravariance would break `get`. (Lecture 1, §3–4.)

**Q5 — B.** `inline` copies the function body and each lambda argument's body into the call site, eliminating the `Function` object allocation. That copy is also what enables non-local returns and reified types. (Lecture 2, §1.)

**Q6 — B.** Reification substitutes the concrete type into the inlined body at each call site, where the type is known. No `inline`, no call-site substitution, so `T` stays erased — hence the requirement. (Lecture 2, §3.)

**Q7 — C.** Inside an `inline fun <reified T>`, `is T`, `as T`, and `T::class` all work because the concrete type is substituted per call site. You cannot put `reified` on a class or store `T` — reification lives only at the call site. (Lecture 2, §3.)

**Q8 — B.** `crossinline` keeps the lambda inlined (no allocation) but forbids non-local return, because the lambda is invoked from another execution context where returning from the enclosing function would be unsound. (Lecture 2, §4.)

**Q9 — B.** `noinline` opts one lambda out of inlining so it remains a real `Function` object you can store in a field/list or forward to a non-inline API — exactly the event-bus handler case. (Lecture 2, §4; mini-project Milestone 1.)

**Q10 — B.** SAM conversion: `Runnable` is a Java single-abstract-method interface, so Kotlin wraps the lambda in a `Runnable` instance automatically. (Lecture 2, §5.)

**Q11 — B.** Kotlin interfaces don't SAM-convert by default; you must declare `fun interface Validator { ... }`. Then `Validator { it.isNotBlank() }` works. (Lecture 2, §5.)

**Q12 — B.** `context(Logger, Clock)` declares two required context receivers; you provide them with nested `with`, and inside the function `log(...)`/`now()` resolve to them unqualified. Calling it without the context is a compile error — the capability is in the type. (Lecture 2, §6.)

**Q13 — B.** The cast is safe because `post` reaches a handler only via `handlers[event.javaClass]` — the same class the `reified T` used as the key. So when the handler runs, its `Any` argument is genuinely a `T`. The reified type tied handler to key; that's what makes the one internal cast sound and the public API cast-free. (Lecture 2, §7; mini-project Milestone 3.)
