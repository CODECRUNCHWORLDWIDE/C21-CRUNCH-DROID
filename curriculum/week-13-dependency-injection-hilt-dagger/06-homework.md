# Week 13 Homework

Six practice problems that revisit the week's topics. The full set should take about **5 hours** in total. Work in your Week 13 Git repository so each problem produces at least one commit you can point to later.

Each problem includes:

- A short **problem statement**.
- **Acceptance criteria** so you know when you're done.
- A **hint** if you get stuck.
- An **estimated time**.

All code targets Kotlin 2.1+, Hilt 2.52+, KSP, JDK 17, AGP 8.7+. Every problem must build with **0 warnings**.

---

## Problem 1 — Read the generated component

**Problem statement.** Using the mini-project graph (or exercise 1's app), build it, then locate and inspect the generated Dagger component. Write your findings into `notes/generated-graph.md`: the path to the generated sources, the name of the generated singleton component class, one `*_Factory` class you found and what it constructs, and one sentence on what the `Dagger<App>_HiltComponents_SingletonC` class represents. Add a second sentence: which tool wrote those files, and how do you know?

**Acceptance criteria.**

- `notes/generated-graph.md` exists with the path, the component class name, a named factory, and the two sentences.
- The class names are quoted from your actual `build/generated/` output, not invented.
- Committed.

**Hint.** After a build, look under `app/build/generated/ksp/debug/kotlin/` (KSP) or `.../kapt/`. The `Hilt_` and `*_Factory` files are generated by the annotation processor — that's your evidence for "which tool". Search for `SingletonC` to find the assembled component.

**Estimated time.** 30 minutes.

## Problem 2 — `@Binds` vs `@Provides`, measured in generated code

**Problem statement.** For one interface→impl pair, write the binding *twice* in two branches: once with `@Provides` (returning `new Impl(...)`) and once with `@Binds`. Build each, open the generated factory for the binding, and write a one-line comparison into `notes/binds-vs-provides.md`: what code each generated, and why `@Binds` produces less. State which one you'd use in production and why.

**Acceptance criteria.**

- Both variants compile and the app works identically.
- `notes/binds-vs-provides.md` describes the generated difference (the `@Provides` variant generates a factory class with a `get()` that constructs the impl; the `@Binds` variant generates no extra factory — the impl's own factory is reused).
- A one-line production recommendation (`@Binds` for interface→impl).
- Committed.

**Hint.** Build the `@Provides` variant, find `<Module>_Provide<Name>Factory`. Switch to `@Binds`, rebuild, and confirm that factory is gone — the interface key now points straight at `Impl_Factory`. That absence *is* the win.

**Estimated time.** 40 minutes.

## Problem 3 — Three scopes, three lifetimes

**Problem statement.** In a small app, create three bindings of a `Counter` type (each just increments a shared int on construction): one `@Singleton`, one `@ActivityRetainedScoped`, one unscoped. Inject all three into a screen, rotate the device, and observe which counters keep their value and which reset. Write the observations and the explanation into `notes/scope-lifetimes.md`.

**Acceptance criteria.**

- Three `Counter` bindings with the three scopes, injected and displayed.
- `notes/scope-lifetimes.md` records what happened to each across a rotation and explains it (`@Singleton` survives — process lifetime; `@ActivityRetainedScoped` survives rotation — ViewModel-like lifetime; unscoped is re-created on every injection).
- 0 warnings. Committed.

**Hint.** Give each `Counter` a static counter it bumps in `init`, and display each instance's captured number. Rotate the emulator (Cmd+Left/Right or the rotate button). The `@Singleton` and `@ActivityRetainedScoped` numbers stay; the unscoped one changes if you re-inject.

**Estimated time.** 50 minutes.

## Problem 4 — Inject a dispatcher behind a qualifier

**Problem statement.** Create a `@Dispatcher(IO)` / `@Dispatcher(Default)` qualifier pair that provides `CoroutineDispatcher`s, and inject `@Dispatcher(IO)` into a repository that does suspend work. Then write a unit test (no Hilt) that constructs the repository with a `StandardTestDispatcher` to prove the injection point makes the class testable.

**Acceptance criteria.**

- A typed `@Qualifier annotation class Dispatcher(val value: AppDispatcher)` with an enum, and `@Provides` for IO and Default.
- A repository whose constructor takes `@Dispatcher(AppDispatcher.IO) CoroutineDispatcher` and uses it for `withContext`.
- A passing unit test that injects a `StandardTestDispatcher` directly (no Hilt) and advances it.
- 0 warnings. Committed.

**Hint.** The repository: `withContext(ioDispatcher) { ... }`. The test: `NotesRepository(testDispatcher, fakeApi)` and `testScheduler.advanceUntilIdle()`. The point is that injecting the dispatcher (vs calling `Dispatchers.IO` inline) is exactly what makes the suspend code deterministically testable.

**Estimated time.** 45 minutes.

## Problem 5 — Assisted injection for a runtime-keyed object

**Problem statement.** Build an `@AssistedInject` `OrderProcessor` that needs an injected `PaymentGateway` (graph) and a runtime `orderId` (assisted), with an `@AssistedFactory`. Inject the factory into a `@HiltViewModel`, create a processor from a `savedStateHandle["orderId"]`, and write a test that the factory threads the id through while sharing the gateway.

**Acceptance criteria.**

- `OrderProcessor` with `@AssistedInject` constructor, `@Assisted orderId`, and an `@AssistedFactory OrderProcessorFactory`.
- A `@HiltViewModel` that injects the factory and calls `create(orderId)` from the `SavedStateHandle`.
- A passing test: build two processors for two ids, assert each resolved the right id and both share the one injected gateway.
- 0 warnings. Committed.

**Hint.** The ViewModel: `private val processor = factory.create(checkNotNull(savedStateHandle["orderId"]))`. The test can use the hand-written factory pattern from exercise 3 if you don't want full Hilt test infra — the assertion is "different id per processor, same gateway instance".

**Estimated time.** 50 minutes.

## Problem 6 — Provoke and read every DI error class

**Problem statement.** Deliberately provoke each of the three canonical Hilt build errors — `MissingBinding`, `DuplicateBindings`, and a scope mismatch (`IncompatiblyScopedBindings`) — one at a time. For each, paste the exact error into `notes/di-errors.md`, identify the offending annotation, and write the one-line fix.

**Acceptance criteria.**

- `notes/di-errors.md` has all three error categories, each with: the pasted compiler error, the root cause (which annotation), and the one-line fix.
- The app builds clean again at the end (all three provocations reverted).
- Committed.

**Hint.** `MissingBinding`: delete a `@Provides`. `DuplicateBindings`: add a second un-qualified `@Provides` of an existing type. Scope mismatch: put `@Singleton` on a `@Provides` in a `@InstallIn(ActivityComponent::class)` module. Read each error bottom-up; the chain names the edge.

**Estimated time.** 45 minutes.

## Rubric

Each problem is graded out of the same five points; the week's homework is out of 30.

| Points | Meaning |
|-------:|---------|
| 5 | Meets every acceptance criterion, builds with 0 warnings, code is idiomatic Kotlin/Hilt, and the written explanation (where asked) is correct and in your own words. |
| 4 | Meets all criteria but with a minor non-idiomatic choice (e.g. `@Provides` left where `@Binds` was better, a `@Named` string qualifier where a typed annotation was cleaner, an unnecessary scope). |
| 3 | Works, but misses one criterion (e.g. scope observations recorded but not explained, dispatcher injected but the test still touches a real dispatcher, assisted factory builds but doesn't share the graph dep). |
| 2 | Compiles and partially works; a core idea is wrong (field injection where constructor injection was the point; everything `@Singleton` "to be safe"). |
| 1 | Does not build, or the approach fundamentally misunderstands the topic. |
| 0 | Not attempted. |

**Crosscutting deductions** (apply to any problem): **−2** for any DI error worked around by `@Suppress` or by deleting a needed binding instead of fixing the wiring; **−2** for a `@Singleton` that holds an Activity context (a leak); **−1** for field injection where constructor injection was available.

**Target: 24/30.** Below that, the two ideas to revisit are almost always the same two the quiz grades on — "Hilt is Dagger underneath, read the generated graph and the errors" (problems 1, 2, 6) and "scope and qualify deliberately" (problems 3, 4, 5) — so re-run exercises 1 and 2 before resubmitting.
