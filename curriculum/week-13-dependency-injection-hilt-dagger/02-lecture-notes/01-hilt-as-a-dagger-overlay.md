# Lecture 1 — Hilt as a Dagger overlay: what it solves, and what it still hides

> "Hilt isn't a new dependency injector. It's a curated set of Dagger components someone already wired correctly so you don't have to."

This is the lecture that decides whether Hilt feels like magic or like a tool you can reason about. The framing for the whole week is one sentence: **Hilt is a Swift-thin— sorry, a Kotlin-thin — opinionated layer over Dagger.** Hold that, and every surprise this week — why a binding is "not provided", why a scope mismatch fails to compile, why the generated class is named `Hilt_MainActivity`, why a `@Provides` in the wrong component is invisible — has a one-layer-down explanation. Lose it, and you are cargo-culting `@Inject` annotations and praying the build goes green.

We are going to build the mental model bottom-up: the engine (Dagger, a compile-time annotation processor), then the overlay (Hilt's predefined components and entry points), then the declarations (`@Inject`, `@Module`, `@Provides`, `@Binds`), then `@InstallIn` and the component hierarchy. By the end you should be able to draw the component tree on a whiteboard and point to which component is responsible for any given binding's lifetime.

---

## 1. The stack, drawn once so we never have to argue about it again

Here is the full stack under a Hilt app, top to bottom:

```text
┌─────────────────────────────────────────────────────────────┐
│  Your Android code                                           │
│    @AndroidEntryPoint class MainActivity                     │
│    @HiltViewModel class FeedViewModel @Inject constructor    │
│    class NotesRepository @Inject constructor(...)            │
├─────────────────────────────────────────────────────────────┤
│  Hilt (the opinions + generated Android glue)                │
│    @HiltAndroidApp / @AndroidEntryPoint / @HiltViewModel     │
│    Predefined components: SingletonComponent, ActivityRet... │
│    Predefined scopes: @Singleton, @ViewModelScoped, ...      │
│    @InstallIn -> which component a @Module lives in          │
├─────────────────────────────────────────────────────────────┤
│  Dagger (the engine — present, just not spelled out)         │
│    @Component / @Subcomponent (Hilt generates these)         │
│    @Module / @Provides / @Binds (you write these)           │
│    *_Factory classes, the directed binding graph             │
│    Compile-time validation: every edge must resolve          │
├─────────────────────────────────────────────────────────────┤
│  KSP / kapt (the annotation processor that runs at build)    │
│    reads your annotations, writes Kotlin/Java source         │
│    DaggerApp_HiltComponents, Hilt_MainActivity, *_Factory    │
└─────────────────────────────────────────────────────────────┘
```

You never type a single raw Dagger `@Component` in a Hilt app. But every one of them is *there*, generated by the processor, holding your bindings, validated at compile time. When you open `app/build/generated/ksp/debug/kotlin/` (do this — it is on the resources page) you will find `Hilt_MainActivity`, `FeedViewModel_Factory`, and a `DaggerApp_HiltComponents_SingletonC`. That generated graph is Dagger's, untouched in spirit since 2015. Hilt wrote those components *for* you.

**Why does this matter for you, the engineer?** Because the moment a build fails with a DI error, the error message is **Dagger's**. It says `MissingBinding` or `DuplicateBindings` or `... was bound multiple times`, with a Dagger stack of which component was resolving which edge. The Hilt docs are good but thin; the Dagger docs and a decade of Stack Overflow on the exact same error messages are deep. Knowing the lineage doubles the surface area of help available to you.

## 2. What Hilt actually solves

Dagger is powerful and *miserable* to set up by hand. The pre-Hilt ritual was:

- Hand-writing `@Component` interfaces and `@Subcomponent`s, and wiring their parent/child relationships yourself.
- A `@Component.Factory` to pass the `Application` in, and then storing the component on your `Application` subclass so the rest of the app could reach it.
- Field injection in every `Activity`: `(application as MyApp).appComponent.inject(this)` in `onCreate`, before `super.onCreate`, in the right order, or it crashed.
- Defining `ActivityComponent` / `FragmentComponent` subcomponents and their scopes by hand, and getting the scope annotations consistent across thirty modules.
- A `ViewModelComponent` and a multibound `ViewModel` factory map, hand-assembled, because Dagger didn't know about `ViewModel` at all.

Every team that adopted Dagger wrote roughly the same 400 lines of component boilerplate, and roughly every team got some of it subtly wrong. Hilt is Google looking at that and saying: **we will write the components for you, once, correctly, with sensible scopes, and you will just install your bindings into them.** That is the entire value proposition. Hilt is opinionated Dagger, where the opinions are "here are the components every Android app needs, already wired."

Here is the headline win in code. The whole DI setup for an app is now four annotations:

```kotlin
// 1. The Application — Hilt generates the SingletonComponent off this.
@HiltAndroidApp
class CrunchApp : Application()

// 2. An Activity — Hilt generates Hilt_MainActivity and does field injection.
@AndroidEntryPoint
class MainActivity : ComponentActivity() {
    @Inject lateinit var analytics: Analytics   // field-injected by Hilt
    // ...
}

// 3. A ViewModel — Hilt bridges to the Jetpack ViewModel factory.
@HiltViewModel
class FeedViewModel @Inject constructor(
    private val repository: FeedRepository,      // constructor-injected
    private val savedStateHandle: SavedStateHandle
) : ViewModel()

// 4. A plain class — the graph constructs it directly, no module needed.
class FeedRepository @Inject constructor(
    private val api: FeedApi,
    private val dao: FeedDao
)
```

That replaces the 400 lines of component boilerplate. No `@Component`. No subcomponent wiring. No `(application as MyApp).appComponent.inject(this)`. You annotate, and Hilt generates the graph. This is the correct default for a new Android app in 2026.

### What about Koin? kotlin-inject? Metro?

One honest paragraph, because you will be asked. **Koin** is a *runtime* service locator — it resolves dependencies at runtime from a DSL, which means a missing binding crashes at runtime, not compile time, and it is slightly slower at resolution. People like it for its simplicity and zero annotation processing. **kotlin-inject** and **Metro** (Zac Sweers' newer work) are *compile-time* DI like Dagger but Kotlin-native, often faster to build. All three are real, defensible choices. But Hilt is the Android default, it is what Now-In-Android uses, and it is the capstone target — so it is what we teach. The skill transfers: a graph is a graph, scopes are scopes, regardless of the framework that builds it.

## 3. `@Inject` — the default, and why constructor injection wins

`@Inject` on a **constructor** is the centre of gravity. It tells the graph: "you already know how to build everything this constructor needs, so you can build this type too." The graph reads the constructor parameters, recursively resolves each one, and synthesises a `*_Factory` that constructs the object.

```kotlin
class FeedRepository @Inject constructor(
    private val api: FeedApi,           // graph resolves this...
    private val dao: FeedDao,           // ...and this...
    private val clock: Clock            // ...and this, recursively.
)
```

For this to work, *each* of `FeedApi`, `FeedDao`, and `Clock` must itself be resolvable — either it has its own `@Inject constructor`, or a module `@Provides`/`@Binds` it. The graph is a directed graph of these edges; Dagger walks it at compile time and proves every edge resolves. A missing edge is a `MissingBinding` build error pointing at the parameter it couldn't satisfy.

There is a subtle but important consequence here that trips up people coming from a runtime DI framework like Koin or Spring: **the entire graph is validated at build time, before the app ever runs.** Dagger does not "try to resolve a dependency when it's first needed" the way a runtime container does. It computes the whole transitive closure of every injection site at compile time and refuses to produce a class file if any edge is unresolved. This is the property that makes compile-time DI worth the annotation-processing cost: the class of bug "I forgot to provide a dependency and it blew up in production three weeks later" is structurally impossible. The graph is either complete — and the build is green — or incomplete, and the build is red with the exact missing edge. There is no third state where it compiles but crashes for a missing binding.

There is a second injection mechanism, **field injection**, and you use it *only* where you cannot use a constructor — namely Android framework types you do not construct (Activity, Fragment, Service, BroadcastReceiver). You cannot write `MainActivity @Inject constructor(...)` because the OS constructs your Activity, not you. So Hilt field-injects:

```kotlin
@AndroidEntryPoint
class MainActivity : ComponentActivity() {
    @Inject lateinit var analytics: Analytics   // set by Hilt before onCreate runs
}
```

**The rule: prefer constructor injection everywhere you can; fall back to field injection only for framework-constructed types.** Constructor injection has three wins. First, dependencies are explicit and final — you can see everything the class needs by reading its constructor. Second, the class is **testable without Hilt at all** — in a unit test you just call `FeedRepository(fakeApi, fakeDao, fixedClock)`. Third, there is no `lateinit` window where the field is null. Field injection sacrifices all three; use it only where the platform forces your hand.

This is why Week 12's ViewModel lecture was load-bearing. A `@HiltViewModel` is a normal constructor-injected class — Hilt just bridges it to the `ViewModelProvider.Factory` so that `hiltViewModel()` in Compose (or `by viewModels()` in a Fragment) hands you a fully-wired instance.

## 4. `@Module`, `@Provides`, `@Binds` — teaching the graph what it can't construct

Constructor injection covers types *you* own. It does not cover:

- **Interfaces.** The graph cannot construct `FeedApi` if `FeedApi` is an interface — there is no constructor to call.
- **Third-party classes.** You cannot put `@Inject` on `OkHttpClient`'s constructor; you don't own its source.
- **Configured singletons.** Even for a type you own, you sometimes want to *configure* it (a `Retrofit` with a specific base URL and converter) rather than let the graph guess.

For all three you write a **module** — a class (or `object`) annotated `@Module` that contains binding methods.

### `@Provides` — for configured and third-party types

`@Provides` is a function you write whose body constructs the thing. The parameters of a `@Provides` function are themselves resolved by the graph, so a provider can depend on other bindings:

```kotlin
@Module
@InstallIn(SingletonComponent::class)
object NetworkModule {

    @Provides
    @Singleton
    fun provideOkHttpClient(): OkHttpClient =
        OkHttpClient.Builder()
            .connectTimeout(15, TimeUnit.SECONDS)
            .build()

    @Provides
    @Singleton
    fun provideRetrofit(client: OkHttpClient): Retrofit =   // client comes from the graph
        Retrofit.Builder()
            .baseUrl("https://api.crunch.example/")
            .client(client)
            .addConverterFactory(
                Json.asConverterFactory("application/json".toMediaType())
            )
            .build()

    @Provides
    @Singleton
    fun provideFeedApi(retrofit: Retrofit): FeedApi =
        retrofit.create(FeedApi::class.java)
}
```

Notice the dependency chain entirely inside the module: `provideFeedApi` needs a `Retrofit`, which `provideRetrofit` builds from an `OkHttpClient`, which `provideOkHttpClient` builds. The graph stitches them. You never call these functions; Dagger calls them in the right order from the generated factory.

### `@Binds` — for interface-to-implementation, and why it's cheaper

When all you are doing is saying "when someone asks for the interface `FeedRepository`, give them the implementation `FeedRepositoryImpl`," `@Provides` works but is wasteful — it generates a factory that just news up and returns the impl. `@Binds` expresses the same thing as an **abstract** function with no body, and Dagger optimises it to a direct cast with no factory at all:

```kotlin
@Module
@InstallIn(SingletonComponent::class)
abstract class RepositoryModule {

    @Binds
    abstract fun bindFeedRepository(impl: FeedRepositoryImpl): FeedRepository
    //                                    ^ must have its own @Inject constructor
}

interface FeedRepository { suspend fun latest(): List<Post> }

class FeedRepositoryImpl @Inject constructor(
    private val api: FeedApi
) : FeedRepository {
    override suspend fun latest(): List<Post> = api.getFeed()
}
```

Two rules to internalise:

1. **`@Binds` lives in an `abstract class` (or interface); `@Provides` lives in an `object` (or class with instances).** You cannot mix an abstract `@Binds` and a concrete `@Provides` in the same `object` — they need different containers. A common pattern is two modules, or `@Binds` in an abstract class and `@Provides` in a companion `object`.
2. **`@Binds`'s parameter must itself be injectable.** `FeedRepositoryImpl` must have an `@Inject constructor` (or be provided), because `@Binds` only *renames* an existing binding to its interface; it does not construct anything.

**Prefer `@Binds` for interface→impl; use `@Provides` for everything you actually construct or configure.** `@Binds` generates less code and is the idiomatic choice for the repository/interface pattern that dominates a layered app.

## 5. `@InstallIn` and the component hierarchy — where a binding lives

Every Hilt module must declare **which component it installs into** with `@InstallIn`. The component determines two things: the *lifetime* of any scoped binding in the module, and *who can inject* those bindings. Here is the predefined hierarchy Hilt generates, parent at the top:

```text
SingletonComponent              (lives as long as the Application)
   │
   └── ActivityRetainedComponent   (survives configuration change; ViewModel-ish lifetime)
          │
          ├── ViewModelComponent      (one per ViewModel)
          │
          └── ActivityComponent       (one per Activity instance; dies on rotation)
                 │
                 └── FragmentComponent    (one per Fragment)
                 │      │
                 │      └── ViewComponent     (one per @WithFragmentBindings view)
                 │
                 └── ViewComponent (no-fragment)
   │
   └── ServiceComponent           (one per Service)
```

A binding installed in `SingletonComponent` is visible *everywhere* (every child component can see ancestor bindings). A binding installed in `ViewModelComponent` is visible only inside ViewModels and their descendants. This is the inheritance rule: **children see ancestors' bindings; ancestors never see children's.** A `@Provides` in `ActivityComponent` is invisible to a `@Singleton` binding, which is exactly why a `MissingBinding` sometimes means "the binding exists, but in a component your injection site can't see."

Choosing the component:

| You're providing... | Install in |
|---|---|
| App-wide singletons (`OkHttpClient`, `RoomDatabase`, `Retrofit`) | `SingletonComponent` |
| Something scoped to a ViewModel's lifetime | `ViewModelComponent` |
| Something tied to one Activity instance (an `ActivityResultLauncher` wrapper) | `ActivityComponent` |
| Something a Service needs | `ServiceComponent` |

In a layered app the overwhelming majority of your `:core-*` bindings go in `SingletonComponent` — a database, a network client, a repository are application-lifetime things. We will see in lecture 2 that *over*-scoping (making everything `@Singleton`) has a memory cost, but for *installation*, `SingletonComponent` is the common, correct default for shared infrastructure.

## 6. The entry-point annotations — what each one generates

Three annotations bridge Hilt to the Android framework. Knowing what each *generates* demystifies the rest.

### `@HiltAndroidApp` — the root

```kotlin
@HiltAndroidApp
class CrunchApp : Application()
```

This generates `Hilt_CrunchApp` (the real base class your `CrunchApp` ends up extending, via a bytecode transform) and, crucially, the **`SingletonComponent`** — the root of the whole graph, created when the process starts and living as long as the application. Without `@HiltAndroidApp` there is no graph; it is the first annotation in any Hilt app, and forgetting it produces a build error telling you exactly that.

### `@AndroidEntryPoint` — field injection into framework types

```kotlin
@AndroidEntryPoint
class FeedActivity : ComponentActivity() {
    @Inject lateinit var analytics: Analytics
}
```

This generates `Hilt_FeedActivity`, a base class that, in `onCreate`, asks the appropriate component for the `Analytics` binding and sets the field — before your code runs. `@AndroidEntryPoint` works on `Activity`, `Fragment`, `View`, `Service`, and `BroadcastReceiver`. The rule: **if a framework type wants injected fields, it needs `@AndroidEntryPoint`, and so does its host.** A Fragment annotated `@AndroidEntryPoint` must live in an Activity that is also `@AndroidEntryPoint` — the components are nested, and Hilt enforces it.

### `@HiltViewModel` — the ViewModel bridge

```kotlin
@HiltViewModel
class FeedViewModel @Inject constructor(
    private val repository: FeedRepository,
    private val savedStateHandle: SavedStateHandle   // Hilt provides this automatically
) : ViewModel()
```

This registers the ViewModel with Hilt's generated `ViewModelProvider.Factory`, so that `by viewModels()` (Fragment) or `hiltViewModel()` (Compose, via `hilt-navigation-compose`) returns a fully-injected instance scoped correctly to the `ViewModelComponent`. Note `SavedStateHandle` is special — Hilt knows how to provide it without you declaring a binding, because it comes from the ViewModel owner. This is the cleanest integration in the framework and the one you will use most.

## 7. What Hilt still hides — the leaks to know about

Hilt is a good abstraction, which means it leaks in predictable places. Senior engineers know where:

1. **The error messages are Dagger's.** A scope mismatch or missing binding prints a Dagger error mentioning components you never typed (`...SingletonC`, `...ViewModelCImpl`). The fix is to read it as Dagger (§1): which component was resolving which edge, and why couldn't it.
2. **The generated graph is invisible until you look.** You write annotations; you do not see the `*_Factory` or the component tree unless you open `build/generated/`. When wiring is confusing, *read the generated code* — it is plain, mechanical Kotlin/Java.
3. **Scope rules are enforced but unintuitive.** A `@Singleton`-scoped `@Provides` in a `@InstallIn(ActivityComponent::class)` module is a *compile error*, because a scope must match its component. Lecture 2 is largely about this pairing.
4. **Build time.** Annotation processing (KSP/kapt) runs on every build that touches the graph. In a thirty-module app, a single new binding can trigger a non-trivial recompile. KSP is much faster than kapt (use it), but DI is not free at build time.
5. **It is Android-only.** Hilt depends on the Android components. Your `:shared-core` KMP module (Week 19) cannot use Hilt in `commonMain`; it uses constructor injection by hand or a KMP-friendly DI. Hilt is for the `:app` and Android feature modules.

None of these are reasons to avoid Hilt. They are the things you keep in your peripheral vision so that when the abstraction leaks, you recognise the puddle instead of staring at it.

## 8. The decision table

When do you use which mechanism? Memorise the shape:

| Situation | Reach for |
|-----------|-----------|
| A class you own, all deps injectable | `@Inject constructor` — no module |
| An interface bound to one implementation | `@Binds` in an abstract module |
| A third-party type (`OkHttpClient`) | `@Provides` in an `object` module |
| A configured singleton (`Retrofit` with base URL) | `@Provides @Singleton` |
| Two bindings of the same type | `@Qualifier` (lecture 2) |
| A type needing graph deps *and* runtime args | `@AssistedInject` (lecture 2) |
| A framework type wanting injected fields | `@AndroidEntryPoint` + `@Inject` field |
| A ViewModel | `@HiltViewModel` + `@Inject constructor` |
| Reaching the graph from a non-Hilt type | `@EntryPoint` + `EntryPointAccessors` (lecture 2) |
| Code in `commonMain` of a KMP module | **Not Hilt** — constructor injection by hand |

That last row matters for this track specifically: your shared KMP core from Phase 4 does **not** use Hilt. Hilt is an Android-platform DI framework, and the predefined components are Android components. The shared core uses plain constructor injection (a hand-written factory), and the `:app` module's Hilt graph `@Provides` the shared core's types into the Android side. Do not try to `@HiltAndroidApp` your way across the KMP boundary.

## 9. Recap — the one-layer-down habit

You will write Hilt all week. The discipline that turns you from someone who *uses* Hilt into someone who can *debug* it is the reflex to ask, on every surprise, "what is Dagger doing one layer down?"

- Build fails `MissingBinding` → which parameter couldn't resolve, and is it provided in a component the injection site can see? (§5.)
- Build fails `DuplicateBindings` → two `@Provides`/`@Inject` for the same type with no qualifier. (Lecture 2.)
- Build fails on a scope → a scoped `@Provides` whose scope doesn't match its `@InstallIn` component. (Lecture 2.)
- `@Inject lateinit var` is null → the host isn't `@AndroidEntryPoint`, or you read the field before `super.onCreate`. (§6.)
- The generated class is `Hilt_MainActivity` → that's the base Hilt synthesised to do field injection; it is supposed to be there. (§6.)

Hilt solved the component boilerplate and the field-injection ceremony. It did not repeal the laws of the Dagger graph underneath. Learn the graph well enough to read it, write the annotations every day, and you have the skill this week earns: declare a dependency, scope it correctly, and debug the wiring when it breaks.

In lecture 2 we go deeper: scopes and their exact lifetimes, qualifiers for ambiguous bindings, assisted injection for the runtime-argument case, `@EntryPoint` for reaching the graph from outside it, and the multi-module topology the mini-project builds — plus reading the generated Dagger code to debug a real `MissingBinding`. Bring this component-tree diagram with you; we are about to use every node of it.

## 10. Appendix — why dependency injection at all, in one honest paragraph each

It is worth being precise about *why* this whole apparatus exists, because "use Hilt because everyone does" is not an engineering reason and you will be asked for a real one. Dependency injection, stripped of frameworks, is a single discipline: **a class does not construct or look up its own collaborators; it receives them.** A `FeedRepository` that writes `val api = RetrofitFeedApi()` inside itself has welded itself to that exact implementation forever — you cannot test it without a real network, you cannot swap the implementation, and you cannot see what it depends on without reading its whole body. A `FeedRepository` that takes `api: FeedApi` in its constructor has *inverted* that control: it states its needs and lets whoever builds it decide how they're satisfied. That inversion is the entire idea, and it predates Dagger, Hilt, and Android by decades. Everything Hilt adds is machinery to do that inversion at scale without writing hundreds of factory functions by hand.

So the value chain is: constructor injection makes a class **testable** (pass fakes in a test), **flexible** (swap implementations behind an interface), and **honest** (its dependencies are visible in its constructor signature). A graph framework like Dagger then automates the tedious part — figuring out the construction order and wiring hundreds of these constructors together — and validates the whole thing at compile time so a missing piece is a build error. Hilt then removes the Dagger boilerplate for the Android-specific components. Read the value bottom-up: the framework is in service of the discipline, not the other way around. A team that adopts Hilt but still writes classes that look up their own dependencies through a static accessor has bought the machinery and skipped the point.

## 11. Appendix — the cost side, stated plainly

No abstraction is free, and a senior engineer can name the costs of the one they're recommending. Hilt's costs are real and worth stating so you adopt it with open eyes. **Build time:** annotation processing (KSP) runs whenever the graph changes, and in a large multi-module project a single new binding can trigger recompilation across modules because Hilt aggregates the whole graph. KSP is far faster than the old kapt, but DI is not free at build time, and very large graphs are a measurable fraction of a clean build. **Cognitive load:** the indirection that makes the code flexible also makes it harder to answer "where does this instance actually come from?" — the answer is "the graph," and finding the specific `@Provides` means knowing the conventions or reading the generated component. **Error legibility:** the errors are Dagger's, they mention generated components you never typed, and a newcomer reads them as a wall rather than a sentence until they learn the pattern (which is exactly the skill this week teaches). **Lock-in:** once a codebase is wired through Hilt, moving off it is a large mechanical change.

None of these outweigh the benefits for the kind of app this track builds — a multi-module, multi-team, testable, production Android app is precisely where compile-time DI earns its keep, and it is the industry default for good reasons. But the honest framing is a trade, not a free win: you pay build time and a learning curve, and you buy testability, compile-time safety, and a wiring layer that scales to thirty modules without becoming a tangle. For a tiny single-screen app, that trade can go the other way, and "we used plain constructors and a hand-written factory" is a legitimate answer for something small. Knowing *when* the trade pays — and being able to say so out loud — is part of the senior judgment this week is building, not just the mechanics of the annotations.
